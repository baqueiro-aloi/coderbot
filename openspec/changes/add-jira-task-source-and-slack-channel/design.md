## Context

See `proposal.md` for motivation and `specs/` for the behavior contract. `src/task_source.py` already dispatches a function-shaped backend contract with stable `item_id`/`item_url`; `src/main.py` still calls `gmail_client` directly at the task-send, wait, command, status, ping, and stale-reply sites. `data/state.json` and `data/holds.json` persist task/hold state; a tick may spend up to the agent timeout inside a synchronous subprocess. Each installation owns its own `data/` and its own Slack app. GitHub continues to own branches and PRs, and large evidence videos use Drive.

The GitHub task-source change remains active (`add-github-projects-task-source`, one live validation item unchecked); its existing `task_source` contract and issue-based activity trail form the integration baseline. The only archived main spec relevant to this change is `quality-gates`; its email-specific requirements receive complete MODIFIED deltas here. `scripts/setup.sh` currently prompts for a fixed subset of options and rewrites `.env` with only those keys, losing advanced and unknown values; `.env.example` documents more options than the wizard exposes, and `config.py` plus `evidence.py` and `scripts/healthcheck.sh` recognize still more.

## Goals / Non-Goals

**Goals:**
- Leave the FSM's planning, review, merge and retry logic shared across all source/channel combinations.
- Preserve existing Gmail behavior and existing persisted task claims when installations upgrade.
- Make Slack event intake durable independently of long agent turns and ensure thread ownership determines routing.
- Use Jira workflow statuses, not board columns, as the authority for lifecycle decisions.
- Make first-time setup and reconfiguration comprehensive without requiring users to hand-edit `.env` or install a platform-specific native TUI library.

**Non-Goals:**
- Interrupting an in-flight coding-agent subprocess on Slack input.
- Building a common Slack event router or sharing one Slack app between instances.
- Guaranteed distributed lock semantics from Jira labels; the requested label/re-read scheme remains best-effort.
- Relying on GitHub closing keywords to complete Jira issues or mirroring tasks between sources.

## Decisions

### 1. Separate source and conversation façades

Extend `task_source.SOURCES` with a lazy-loaded Jira backend. Introduce a `conversation` façade that delegates to Gmail or Slack based on a separate `CODEBOT_COMM_CHANNEL` (`email` default). Normalize operations needed by `main.py`: open task thread, send with optional files, consume oldest thread reply, poll scoped command, mark processed, drain stale replies, send status and check-in. Email keeps its current subject/thread/processed-message semantics behind an adapter; Slack uses `{channel_id, root_ts}` as an opaque task thread handle. Existing `thread_id` in persisted email tasks remains readable (migrate lazily at call boundaries rather than silently discarding it). Update hard-coded email wording in user-facing strings/prompts to channel-neutral or channel-specific language. Alternative: bolt Slack-only conditionals onto `main.py`; rejected because commands, holds and PR finalization each call Gmail directly today.

Config validation is conditional: Jira vars only in Jira mode, `CODEBOT_USER_EMAIL` only in email mode, Slack bot/app tokens and a public channel ID only in Slack mode. Google OAuth setup remains required for GDoc tasks and for enabled Drive evidence upload, not for a GitHub/Jira + Slack installation with Drive uploads disabled. GitHub `GH_TOKEN` remains required for PRs in every combination.

The pre-task `WAIT_CLEAN` detour has no task thread yet. In Slack mode send a one-time, clearly operational top-level notification without registering its timestamp as an owned task thread, and recheck the tracked git working tree on subsequent ticks; once clean, return to IDLE and pick automatically. Persist an episode flag so a restart does not repeat the warning. The receiver ignores replies to this announcement just like any other out-of-task message. Retain Gmail's existing reply-to-retry behavior unchanged. This avoids broadening the permitted command surface to a second kind of thread.

### 2. Jira REST v3 backend and Jira-specific PR semantics

Authenticate to the configured Jira Cloud site with the account email/API token. Search by project key, configured eligible **status** and required `CODEBOT_JIRA_PICK_LABEL` using paginated `POST /rest/api/3/search/jql` (the legacy `/search` is being removed); also query this instance's claimed non-done issues independently of the opt-in label for state-file recovery. Recheck the opt-in label in search results and in direct issue reads before and after a new claim: search is eventually consistent, and a user may remove the label between listing and claiming. Already-owned issues remain recoverable without that label. Use issue IDs/keys for direct issue reads and writes instead of relying on search read-after-write consistency. Map issue summary to `text`, description to `detail`, stable issue ID to `id`, and key/browser URL to metadata; traverse ADF to render paragraphs, lists, links and attached image references, downloading accessible images best-effort. Preserve `Codebot[n]` title ordering; an optional Jira native priority can be added later without changing the contract.

Use Jira's issue **update operations** to add/remove only the instance's claim/hold labels (never replace the entire labels array). Include readable name **and** persisted installation fingerprint in each label; another fingerprint is a rival even when the name matches. The opt-in label is separate and must survive claim, hold, completion and abort. Re-read the issue after adding a claim label and back off on a foreign owner or missing opt-in label without changing status. Map `eligible`, `active`, `review`, `done` to configurable status names (one eligible status, separate from any board column). Resolve the transition ID *available for that issue* whose destination matches the configured target status; do not try to write the read-only `status` field directly. Validate project access, configured statuses and the presence of an opt-in label setting at startup; report a missing issue-specific transition at use time, since workflows can differ by issue type. Hold swaps ownership labels but retains status; abort restores eligible status and drops claim; done transitions and removes ownership; no operation removes third-party labels. Seed a configurable Jira issue type (default Task), give it the opt-in label, and move it to eligible when creation defaults elsewhere; deduplicate across statuses. Jira comments use ADF; a comment containing the PR URL provides the ticket trail, and `note_pr` moves it to review. Activity comments remain best-effort.

PR body generation becomes source-aware: retain `Closes <GitHub issue URL>` for GitHub-backed tasks; for Jira write `Closes <KEY>` **plus** the Jira browser URL for humans and Jira link detection. This is descriptive text, not a GitHub/Jira auto-transition; `mark_done` alone closes the Jira lifecycle after merge or DONE. Alternative: reuse the generic `Closes <item_url>` line for Jira; rejected because it implies the same GitHub closing semantics and omits the stable Jira key.

### 3. Socket Mode intake with durable thread routing

Start a background Socket Mode receiver using this installation's app token (`xapp-...`) and bot token (`xoxb-...`); subscribe to public-channel message events with `channels:history`. Install the bot in the configured public channel and validate access. The receiver ignores bot/self messages, other channels, top-level human posts and threads it does not own. A local durable SQLite inbox under `data/` (stdlib `sqlite3`) stores thread roots, message IDs/timestamps/text and processed state, with a unique key for Slack event/message deduplication. Commit an accepted event to disk **before** acknowledging it to Slack; acknowledge even ignored events promptly. SQLite's transaction boundary makes redelivery and crashes safe; `state.json` remains the authoritative FSM snapshot, not a queue written concurrently by the receiver.

`main.py` reads queued messages in ascending Slack timestamp, handles one at a time through its current classifiers and only marks an event processed after successful handling; transient failures keep it pending. The receiver signals a wake event to shorten idle/wait sleeps; a running agent turn is never interrupted and queued events wait until it returns. Hold records retain their original thread root; the receiver recognizes active and held roots. A command in a held thread operates on that hold only (CONTINUE flags resume; DONE completes/release; ABORT releases; STATUS reports held state), never on a different active task. Explicitly targeted commands in a foreign thread or top-level messages remain ignored in Slack mode. Existing email-wide fleet semantics remain email-only. On conflict re-finalization, drain queued replies whose timestamps precede the updated PR-ready handoff before inviting a fresh merge decision.

One Slack root per task is created immediately after a successful claim and before exploration starts; it includes instance name, task source link, and a persisted task correlation key. Checkpoint the intended root creation before posting and store returned `root_ts` as soon as the API returns. On uncertain send/crash, reconcile a root by the correlation marker in recent messages posted by *this app* before retrying so the same task does not get duplicate roots. Keep root registrations while a task is active or held; retire them when finished. Alternative: only poll `conversations.replies` during WAIT states; rejected because it cannot receive promptly during long agent turns, misses commands while active, and may face restrictive history/replies rate limits. Alternative: shared Socket Mode connections across installations; rejected because Slack may send an event to any connection, whereas separate apps make delivery and ownership independent.

### 4. Slack delivery and evidence

Map user-facing send sites, check-ins and STATUS to the task's root thread (`thread_ts`); do not create a new top-level Slack message for each phase. Chunk Markdown/proposal/review text along safe boundaries so Slack's text limits never silently truncate an approval request. Upload smaller files with Slack's external file upload flow (`files.getUploadURLExternal` → upload bytes → `files.completeUploadExternal`, specifying `thread_ts`); Drive still receives large mp4 videos, and the thread includes the link. Handle upload failure with an explicit note and preserve the PR handoff. A reply's Slack `user` ID identifies a human; no configured allowlist, as the public-channel membership itself is the user decision. Dedicated bot apps still ignore one another's messages.

### 5. Readable instance names and compatibility

For installations lacking an explicit `CODEBOT_INSTANCE` or persisted `data/instance_id`, generate from curated adjective/animal wordlists with `secrets.choice`, normalize to lowercase ASCII hyphenated words, and persist before using the name. Keep existing persisted `codebot-x7k2`-style names and explicit overrides unchanged. Separately generate and persist a sufficiently long random `data/instance_fingerprint` using `secrets.token_hex`; the installation must retain this file across restarts or restores. Compose each GDoc/GitHub/Jira claim and hold marker from both readable name and fingerprint, while leaving branch names, email subjects and Slack display text readable. Backend owner comparisons use the full pair, never just the name. For pre-upgrade un-fingerprinted markers, migrate only the exact issue/bullet corroborated by this installation's `state.json` or `holds.json`, using each backend's normal claim-race safeguards. A legacy marker without matching local state remains reserved and is reported for manual reconciliation, not silently treated as ours; this intentionally sacrifices automatic recovery of a legacy claim after local state loss. Separate Slack app credentials per installation avoid cross-instance event distribution even when a channel is shared.

### 6. Portable guided setup and configuration inventory

Keep `scripts/setup.sh` as a small POSIX-compatible launcher (also invocable explicitly through `bash scripts/setup.sh` or `zsh scripts/setup.sh`) and put interactive behavior in a host-side Python application. Use a pinned Textual dependency for keyboard-navigable screens, contextual explanations, validation feedback, masked credentials and a final review; select a standard-library line-oriented fallback when Textual is unavailable, `TERM` lacks TUI support, or the user requests text mode. Bootstrap the host venv before launching the UI; a failed optional TUI install MUST NOT block text-mode setup. If stdin cannot take input at all, report how to use an interactive shell rather than writing a partial configuration. Alternative: notcurses or a shell-only UI; rejected because native library installation differs between macOS and Linux and maintaining interactive controls in both bash and zsh would duplicate behavior.

Replace the linear wizard/final-review page with a menu-first Textual app and matching text-mode menu. A section has a draft separate from persisted `.env`; `Test` validates its own required fields plus referenced saved inputs (for example Backlog/GitHub needs Repository's GH_TOKEN), and may use live Jira/Slack/GitHub API checks when selected. The section displays a masked change preview before `Save and Close`. That action re-runs its test, writes only the section's modified keys atomically via the existing lossless EnvFile writer on success, refreshes EnvFile from disk, returns to the menu and displays a checked indicator. On failure it keeps the draft in place and shows an explicit fix, with no write. Discard returns without saving; `Exit` exists only on the menu so no draft is silently retained. A menu-wide `Test` runs full structural validation and selected integration preflights without writing. Changing a saved dependency (GH_TOKEN, target repo, Jira credentials/project, Slack tokens, source/channel, etc.) clears the checked state for dependent sections until retested. Existing credentials remain masked in both UI and text mode. Google OAuth and OpenCode authentication have their own explicit setup actions; missing credentials are reported by relevant section/global tests with guidance to perform those actions.

Build the wizard from a single configuration catalog with env key, scope (source/channel/agent/common/advanced), default, secret flag, validation, explanation and conditional visibility. Primary pages cover target repo + identity, backlog (GDoc/GitHub Projects/Jira), conversation (Gmail/Slack), agent (Claude/OpenCode), GitHub access and evidence/OAuth. An advanced, searchable page lists *all* effective user-settable keys, including keys used outside `config.py`: `CODEBOT_GH_LABEL_PREFIX`, `CODEBOT_GH_ISSUE_REPO`, the four GitHub project statuses, `CODEBOT_ACTIVITY_TRAIL`, `CODEBOT_SELF_HEAL_CODE_REVIEW`, Claude fallback/cooldown, check-in schedule, retries/timeouts, upload/Drive folder, e2e compose filename, environment notes, heartbeat thresholds/data dir and managed runtime path overrides. Show legacy aliases (such as `CODEBOT_CLAUDE_TIMEOUT`) without overwriting them unless explicitly changed; leave derived constants and transient subprocess environment out of the editable catalog. Treat source/channel/agent-specific settings as inactive rather than erasing them when a user switches modes. Verify the catalog against environment reads in `config.py`, `evidence.py`, relevant shell scripts and `.env.example`, with an explicit reviewed allowlist for transient/internal-only variables; tests fail if a new runtime option is missing from both the catalog and documentation. This makes "all settings" an ongoing contract rather than a one-off checklist.

On Jira's backlog page require the nonempty opt-in label beside the site, project and account credentials. After the user enters those credentials, fetch the project's real workflow statuses via Jira Cloud v3 and populate the eligible/active/review/done TUI dropdowns (numbered choices in text mode). Changing the site, project, account or token invalidates the fetched list; failed authentication lets the user correct the values and retry instead of storing guessed statuses. The final configuration preflight reuses that same Jira lookup.

Credential-dependent setup follows the same rule for other selected integrations: request Jira site/account/token before listing projects (key and name) and then their workflow statuses; request a GitHub token before listing accessible Projects v2 boards for the target repo's owner (allow an explicitly entered URL for a different owner). Request both tokens for each Slack app before listing public channels where that bot is a member. Use `auth.test`, `apps.connections.open`, and paginated `conversations.list` with bot scope `channels:read` to validate the app and retrieve channel IDs/names. Offer only joined public channels in the primary wizard; show the bot's workspace and instructions to invite it when there are no usable channels. Present xoxb and xapp creation links directly beside their masked fields (OAuth & Permissions → Bot User OAuth Token; Basic Information → App-Level Tokens, `connections:write`). The TUI uses dropdowns and the text fallback uses numbered choices. Rotate credentials or change owners/projects → invalidate cached options and reload before leaving that page. Do not save an ID from a stale token. Google Docs OAuth and OpenCode provider login are currently performed after the confirmed `.env` is saved; their first-install choices cannot be queried at these pages without changing that authentication sequence.

Slack section testing must distinguish Web API errors instead of collapsing them into "bot must join with channels:history": `missing_scope` names the missing scope and points to OAuth & Permissions/reinstall; `is_member=false` names the channel and how to invite this app's bot; a private or archived channel has its own message; invalid xoxb/xapp tokens identify which credential failed without printing either secret. The selected channel remains a stored ID while the menu shows the human-readable name.

Parse `.env` losslessly enough to retain comments, ordering, inactive keys and unknown keys. Update only keys the user actually changed, never synthesize an empty value over a previously set secret. Before confirmation present a masked diff, validate selected integrations and dependent credentials, then back up the old file and atomically replace it with restrictive permissions. Cancellation or validation failure leaves the original byte-for-byte intact. Reuse existing guided OAuth and OpenCode authentication actions from the UI and offer only the Google APIs actually needed by the chosen source/channel/Drive setting; avoid using a half-written `.env` as a prerequisite for auth or image builds (pass staged values explicitly). Alternative: regenerate `.env` from a fixed shell heredoc; rejected because it currently discards settings unknown to the wizard. The new interactive application runs on the host; the runtime container only receives the selected configuration, not a mandatory TUI dependency.

## Risks / Trade-offs

- **Label add-then-verify is not atomic:** two claims can pass verification at slightly different times → recheck owner before status moves and at startup, back off on observed rivals, document that the requested label scheme is best-effort.
- **Jira search is eventually consistent and workflows may differ by issue type:** recent claims or new seeded issues can be absent from search; a target transition may be unavailable → use direct issue re-reads, idempotent operations and issue-specific transition checks with actionable errors.
- **A Jira issue can lose its opt-in label after discovery:** a stale result could expose unintended work → filter search results and verify the label directly before and after applying the ownership label; refuse new claims without it.
- **Socket Mode can redeliver or disconnect; API calls may succeed before local state is saved:** lost commands or duplicate task roots → persist inbound events before ack, dedupe IDs, reconnect automatically, and reconcile uncertain outbound roots by correlation marker.
- **Slack messages/files and shared-channel traffic have API limits:** a large proposal or burst of unrelated events can crowd the channel → chunk outbound messages, filter events before persistence, honor `Retry-After`, and do not rely on frequent `conversations.replies` polling.
- **Independent generated names can collide:** no shared naming registry exists → persist a separate random fingerprint in every ownership marker and compare the full pair; recover pre-upgrade name-only claims only with corroborating local state.
- **Google scopes vary by combination:** GDoc and Drive still need consent even without Gmail → guide setup based on the selected source/channel and evidence-upload setting; validate only needed credentials.
- **Host terminal/dependency differences:** macOS/Linux shell and term capabilities differ and Textual needs a Python environment → small portable launcher, pinned isolated venv, line-oriented fallback and targeted cross-shell tests.
- **Fixed-list `.env` rewrites currently discard options and may expose secrets during review:** a new or unrecognized key can vanish on reconfiguration → preserve untouched lines, masked previews, backup plus atomic replace, and a source-to-catalog coverage check.
- **No task thread exists when a dirty checkout blocks picking:** the Slack receiver has nowhere to route replies → post one informational announcement outside task threads and autonomously recheck for cleanliness; continue ignoring out-of-task messages.

## Migration Plan

1. Ship façade/backend and Socket Mode receiver behind new opt-in selectors; email and GDoc remain defaults.
2. On upgrade, keep valid saved instance IDs and existing email `thread_id`/hold entries; generate and persist an ownership fingerprint, migrate only locally corroborated legacy claim/hold markers, and treat uncorroborated legacy markers as reserved. New installations generate readable IDs plus fingerprints. No automatic migration of an in-flight email task to a Slack thread or a GDoc/GitHub task to Jira.
3. Launch the portable guided setup on macOS or Linux to configure the selected source, channel and agent and to review all advanced settings; use text mode if TUI support is unavailable. For a new Jira instance configure Jira site/project/account token, the required opt-in label, and statuses selected from the project's real workflow. Label existing Jira issues that should be offered as new tasks. For a Slack instance create its dedicated app, subscribe to public channel messages, enable Socket Mode, install it in the configured channel and provide bot/app tokens. Keep Drive OAuth when evidence uploads or GDoc require it. Preserve previous `.env` values and back it up before saving.
4. Roll back by restoring the previous selectors/credentials and runtime on an idle installation; retain the durable `data/` directory and the original instance ID. Finish or abort in-flight work in its existing channel/source before switching, so no reply thread or claim is orphaned.
