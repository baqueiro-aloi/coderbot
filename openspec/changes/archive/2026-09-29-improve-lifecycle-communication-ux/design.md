## Context

See `proposal.md` and the two delta specs. `main.py` owns the task FSM; `email()` is the shared task-send path through `conversation.send()`. Slack opens a root on pick, while Gmail starts its thread on the first outgoing send. Agent runs and review polling are synchronous. `data/state.json` and `data/holds.json` persist task state; `data/` is git-ignored. The proposal has three send routes (normal, revision, and completion via WAIT_REPLY). `do_open_pr()` can open a PR and enter `WAIT_REVIEW` long before `finalize_pr()` sends the human-review handoff. Existing send paths include activity-trail copies and task-language localization; Gmail caps attachment bytes, Slack uploads files in the task thread.

## Goals / Non-Goals

**Goals:** Give the two transports equivalent, accessible, low-noise task handoffs; derive summaries from existing authoritative inputs; deliver an architectural notice early without altering lifecycle gates. Make proposal packages and notices recoverable across retries/holds/restarts.

**Non-Goals:** A web service, persistent dashboard, interactive Slack approval buttons, a second approval gate for architecture, publishing generated files to the target repo, or relying on a generated report as proof of a passing quality gate.

## Decisions

### 1. Presentation layer separate from the FSM

Add focused modules for artifact packaging, milestone rendering and human-readable report formatting. Keep the existing phase functions and `conversation.send` as the only user delivery path. Map FSM transitions explicitly to eight public milestones: exploring, proposing, awaiting approval, implementing, verifying (including internal review and optional e2e), archiving, PR ready for human review, confirmed merge. Emit standalone notes only when no existing handoff communicates the milestone; the Slack task root may serve as the exploration announcement and Gmail's first announcement opens the thread. A PR's creation gets the separate architecture notice, not a false "PR ready" announcement while automated review is still pending. Retried checks and PR re-finalization reuse the appropriate existing context without repeating milestone art. Alternative: intercept every `state["state"]` assignment or prepend an image to all outgoing messages; rejected because internal waits, retries and loops are not user milestones.

Assets are pregenerated SVG variants with identically labeled PNG renditions; PNG is sent inline in email via a CID HTML alternative with a plain-text stage fallback, and uploaded in the Slack task thread. Text always names the current stage independently of color or image loading. Attachment failures are visible/logged but do not turn a successful work phase into a failure. Keep milestone sent markers in task state and `RESET_KEYS`, and in hold snapshots. Set/check them at explicit send boundaries, persisting a correlation key before ambiguous network calls where transport reconciliation is available. An uncertain Gmail delivery cannot guarantee exactly once without an outgoing message-ID lookup; prefer deduplication and avoid sending an unbounded series of copies. Alternative: generate remote SVG with an external URL; rejected because clients block it and self-contained assets need no hosting.

### 2. Deterministic proposal bundle with bounded revision digest

Resolve only the active change rooted at the validated slug: require the three top-level Markdown files and enumerate `specs/**/spec.md` in stable relative-path order, rejecting symlink escape and absent artifacts. Convert headings and Markdown to sanitized HTML (escape or strip raw HTML and unsafe links), namespace heading anchors by source path, build a sticky left table of contents plus compact client-side expand/search functionality, and embed CSS/JS inline without remote fonts, scripts, or images. Generate an immutable per-round HTML file under `data/` before sending. Check Gmail's configured byte cap up front; if full package cannot be delivered, explicitly request a retry/guidance rather than seek approval based on a silently truncated attachment. The message body remains succinct and readable without opening it.

Persist a per-round snapshot/manifest of source file contents only after a successful proposal send. On revision, compute file/heading/task-level differences from the last **sent** snapshot, and let a constrained summary explain material differences with citations; a deterministic changed-sections list remains the fallback so no change is silently omitted. Share a single proposal-send function across `do_propose`, `do_approval_reply` and `_continue_proposing`. A resume/retry uses the same artifact set until the next successful review send. Alternative: ask the working agent to output the bundle or rely on its free-form recap; rejected because it can omit nested specs or describe unsaved edits.

### 3. Decision-first handoffs use recorded results

Add small templates to compose headings and decision options around the existing message content for approval, questions, stuck recovery and PR merge; preserve existing reply parsing and channel-specific instructions. Keep a verification snapshot from successful `QUALITY_GATE` and `INTERNAL_REVIEW` contracts and the actual e2e suite outcome, not from the narrative. Mark tests/pre-existing failures, optional e2e and unavailable evidence explicitly; do not promote agent claims about the PR review workflow into quality-gate results. Build the PR cover from changed files/commits, task, PR and recorded checks. An evidence index enumerates only attachments accepted for transport and successfully returned Drive URLs, with type-appropriate explanations; missing artifacts receive a labeled note. On requested PR feedback, retain the user's request alongside the queued push context and format a concise request/change/verification recap after the push succeeds. Changes via the WAIT_REPLY continuation follow the same path. Alternative: send the full raw agent output as the only summary; rejected because readers cannot find the decision or what was tested.

### 4. Evidence-backed architecture report follows PR creation

After `pr_url` is known and before entering `WAIT_REVIEW` (or before `finalize_pr` if no review action exists), assemble approved design/proposal/spec context plus committed `base_sha..HEAD` diff and changed-file manifest. A separate read-only analysis turn returns bounded structured candidates with type (decision vs unverified assumption), impact, planned/not planned status, and changed relative file references. Filter invalid JSON, missing paths, paths not in the PR diff, generic/trivial claims and uncited impacts; cap and prioritize the report. Link evidence to the PR's head SHA/path, not to mutable local files; do not expose secrets or arbitrary diff content in the outgoing message. A zero-candidate valid result says no additional significant decisions were found; analysis failure is logged distinctly and must not claim there are none. Store the sent report's decision IDs and head SHA to avoid duplicate notifications on restart. Report generation/delivery is best-effort, with the review wait proceeding regardless.

After automated-review or human-feedback fixes are pushed, compare significant architectural decisions against the last reported version and send a short update only on a material difference. Use the same guard for conflict-resolution pushes. This inspection happens after the push, so links describe the actual PR version. Alternative: extract keywords like `SYS_ADMIN` alone, or summarize only `design.md`; rejected because decisions can be implemented indirectly and the planned design may diverge from the shipped diff.

## Risks / Trade-offs

- Gmail SVG/embedded asset rendering differs from Slack → ship PNG renditions and always include text labels; confirm the MIME image is truly inline in supported clients.
- A large change can exceed the attachment cap or the analyzer's context window → explicitly detect bundle size and missing sources; inspect changed-file manifest and relevant diffs with coverage noted rather than asserting a full review from partial input.
- Files or Markdown may contain script/HTML/link payloads → sanitize Markdown, enforce a fixed artifact allowlist, escape all generated text/paths and restrict links to safe schemes.
- Network send succeeds but state save fails → keep immutable per-round bundles, persisted send markers and transport-specific reconciliation where possible; accept that absolute exactly-once Gmail delivery cannot be promised.
- AI-generated architecture claims can be plausible but false → require a changed-file citation, mark uncertainty, compare approved artifacts, and suppress uncited claims.
- Added milestone messages could reset silence timers and clutter activity trails → emit only once per task/stage and reuse existing messages; keep pings and questions unchanged.

## Migration Plan

Ship new presentation state keys with missing-key defaults for in-flight `state.json` and held-task snapshots. Stage static assets in the bot image; keep generated files under the existing persistent, ignored `data/` directory. Existing tasks continue with their current thread and phase; only future reached milestones get new announcements. Roll back by reverting bot version while retaining `data/`; unknown state fields are ignored by older versions.
